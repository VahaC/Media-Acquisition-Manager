## Highlights

**Schedule the replacement of a copy you already have.** When a release is a better copy of a film
you have, or of episodes of a series you have, the **Download** dialog's new **Replace after
verification** lets the owner tick exactly which of the old copies it should replace. The app writes
the replacement down with the download, before anything reaches qBittorrent, follows it until the
download is done, and then checks the new file. Only once the new file is verified does the old copy
move — aside, into a quarantine you can restore it from, never away. See [Scheduling a
replacement](#scheduling-a-replacement).

**The new file is checked before anything is touched.** Once the download is done, the app checks
each new file by itself: that qBittorrent finished it, that it is a video the app can read, and that
Jellyfin, asked to look at it, has read it and identified it as the very film or episode your old
copy is — by Jellyfin's own ids, never by a file name. Each copy you ticked must pair with exactly
one new file. Jellyfin gets an hour for that; if anything is still missing then, or is wrong or
unclear sooner, the replacement stops and says why, and both copies stay. See [Checking the new
file](#checking-the-new-file).

**The old copy moves aside, into a quarantine, never away.** Once the new file is verified, the app
checks the old copy once more — that it is still the very file you picked, and that no torrent in
qBittorrent holds it — and then renames it, with its own subtitles and `.nfo`, into
`.mam-quarantine` at the top of its media folder: one rename per file, on one mount, that never
replaces a file and never copies one. Anything in the way stops it for review with why, and nothing
is ever deleted because a move couldn't be made. A torrent that still holds the copy is yours to
remove in qBittorrent; then press **Retry**. See [Moving the old copy aside](#moving-the-old-copy-aside).

**Put it back, or delete it for good — you decide, and nothing goes by itself.** A quarantined copy
stays until you choose, on the job's page: **Restore** puts every file back where it was, and
**Delete for good** deletes them from the quarantine after asking once more, naming every file and
the room it frees. No timer deletes anything. See [Restoring or deleting a quarantined
copy](#restoring-or-deleting-a-quarantined-copy).

**When a replacement stops, you see why and settle it.** The **Jobs** page and the job's page now
show where each replacement stands — until what time it waits for Jellyfin, which new file each of
your old copies pairs with, and what stopped it, with what to do. Fix the new item in Jellyfin, or
remove the torrent in qBittorrent, then press **Retry**; **Drop** a copy that can't be paired, which
stays where it is; or **Keep both**, which cancels only the replacement and lets the download go on.
No click moves a file or stands in for Jellyfin's ids. See [When a replacement
stops](#when-a-replacement-stops).

**The owner's, and off until the owner turns it on.** After the upgrade replacement is off and no
folder is ticked. Turning it on takes four steps: mount the media folders read-write, run the app as
their owner, then switch it on and tick the library folders it may touch on the **Media folders**
page. Everyone else keeps **Keep both**, as before. See [Turning it on](#turning-it-on).

**See what stands in the way before you tick.** Each of your copies says whether it can be replaced
and, if not, why; whether a torrent in qBittorrent still holds it, and what you will have to do
about that; and whether moving it would free any room at all. See [What the dialog tells you about
each copy](#what-the-dialog-tells-you-about-each-copy).

**A replacement is sent only when it can land on nothing you have.** A file already where the
release would write stops it — even one with the same bytes —, and so does anything the app can't
look at. Nothing reaches qBittorrent then: the dialog says why, and you pick **Keep both** yourself
if you still want the download. See [When a replacement isn't sent](#when-a-replacement-isnt-sent).

## Scheduling a replacement

Find a release on the **Search** page and choose **Download**. Pick the download client and the
destination as always. Under **Existing copies**, **Keep both** is picked, and stays picked unless
you change it; the summary's **Existing copies** then reads "Kept: nothing is replaced or removed,
and a release that would write over a different file isn't sent."

As soon as a destination is picked, the dialog lists **Your copies** of what the release matched in
your library: the film, with every file of every version; for a TV release, the episodes you have of
what its title claims — one episode, a range within one season such as S02E05–E08, or whole seasons
—, by season, each episode with its versions. Each copy shows its file name and folder, its
version's label or "Version 2", the edition its name says (Theatrical, Extended, Director's Cut…),
its resolution and dynamic range as the app measured them, and its size. The line above says which
edition the release's own title names, if any. Nothing is ticked for you.

Pick **Replace after verification** and tick the copies the release should replace. A season has
**Tick every copy that can be replaced** and **Untick all**, and says how many of its copies are
ticked; with several seasons, each is folded until you open it. Switching back to **Keep both**
keeps your ticks, in case you change your mind again.

When the release matched your film only by its title and year — every Toloka release does, as Toloka
lists no ids —, the dialog also asks you to tick **This release is Alien (1979)**, or for a series
**This release is The Penguins of Madagascar (2008), season 2**. **Send** waits for that tick. It
lets the app schedule the replacement, and nothing more: the old copy will move only once Jellyfin
has given the new file that work's own id. When two of your works would read the same — one film in
two libraries, say —, the words also name the library ("… in “Фільми”") or the copy, so you know
which one you confirm. A release matched by its title alone, or whose ids disagree with your film's,
can't replace anything, and the dialog says so.

The summary lists what you ticked, by work — "Alien (1979): 1 copy", "The Penguins of Madagascar,
Season 2: 18 copies" — with each copy's path, then the conditions: the old copy moves into the
quarantine only once the new one is downloaded, checked and shown in Jellyfin as the same work, a
copy a torrent holds waits until you remove that torrent, and the old copy stays in the quarantine
until you restore it or delete it for good on the job's page. **Send** sends the release to
qBittorrent as before, and writes the replacement down with the download first. If a copy changed in
the meantime — another file put in its place, say — **Send** says which and why, reads your copies
again, and keeps the form.

What happens after that: the replacement follows its download — scheduled, submitted,
downloading, downloaded —, and once the download is done the app checks the new file; see [Checking
the new file](#checking-the-new-file). Once it is verified, the old copy moves into the quarantine;
see [Moving the old copy aside](#moving-the-old-copy-aside). Until then both copies stay where they
are.

## What the dialog tells you about each copy

A copy you can't tick says why under it:

- **"Its folder isn't ticked for replacement on the Media folders page."** — tick its library folder
  there first; see [Turning it on](#turning-it-on).
- **"The app can't reach this file …"** — the file has no path in the app, or lies outside the
  **Media folders**.
- **"Not inspected yet"** — the app needs to have read the file once; on the **Library** page,
  **Inspect files** does it.
- **"Changed since the app inspected it."**, **"The file isn't there any more."** or **"The app
  can't read this file now."** — the app looks at each copy again when the dialog reads it, and
  again when you choose **Send**.
- **"The library places this version outside the episodes this release claims."** — a TV copy
  Jellyfin lists under another season or episode than the release's.
- **"A replacement scheduled earlier already holds this copy."** — another download is already set
  to replace it.
- **"This file is also a copy of another work this release matched, which can't be replaced."** —
  the same file, listed under two of your works, one of which the release can't replace.

A copy that can be replaced also says when it has another name — a hardlink: "This file has another
name, so moving it frees no space." The dialog says it from its first read, whether **Keep both** or
**Replace after verification** is picked, as it needs only the disk.

When you pick **Replace after verification**, the app also asks your download clients which torrents
hold your copies, and marks them:

- **Held by a torrent.** "Held by the torrent “Alien.1979.Remastered.1080p” in “qBittorrent”: before
  this copy can move you'll remove that torrent there without its files — which also stops seeding
  its other files." A season pack holding many of your copies is said once, with how many. You can
  still schedule the replacement — the download takes its time, and you can remove the torrent in
  qBittorrent meanwhile. The app never removes, stops or changes a torrent.
- **A torrent's file.** When a copy's other name is a torrent's file, the dialog names that torrent
  too: "It is the torrent “…”'s file."
- **Couldn't check.** When a client couldn't be asked — switched off, out of reach, or a qBittorrent
  older than 5.2, which can't list its torrents' files in one go — the dialog says so: "Couldn't
  check whether a torrent in “qBittorrent” holds these copies: …". The same goes for torrents whose
  files the app couldn't place in its folders. Either way you can still schedule; nothing is taken
  for "not held".

**Replace after verification** can't be picked at all, and the dialog says why, when replacement is
switched off, for a magnet link (its files are unknown until qBittorrent fetches them), for a
destination whose folder isn't inside a library under the **Media folders** or that the app can't
look into, and for a release that matches no film or held episode of yours. Only the owner sees it
enabled: everyone else reads "Only the installation owner can replace a copy." and sends with **Keep
both**, as before.

## When a replacement isn't sent

Right before the release goes to qBittorrent, the app looks at every place its files would land, as
it does for every download. For a replacement it is strict: **any** file already at one of those
places stops it — even one with the same bytes, since a file replaced by itself is no replacement —,
and so does every place it couldn't look at: a link that leads out of the **Media folders**, a file
name it can't look up, a .torrent whose list of files it can't read, or a qBittorrent that couldn't
list the downloads it already has in that category. So does a release whose download link turns out
to be a magnet, and a category whose folder isn't inside a library.

Then nothing reaches qBittorrent. The dialog keeps your choices and says why, such as "“qBittorrent”
would write over “Alien (1979).mkv” in the folder of the category “Movies”: a file is already there,
and a replacement never lands on a file already there, so nothing was sent." The job is listed on
**Jobs** as **Failed** with the same sentence, and its replacement as stopped. The app never sends
it as a plain download on its own: pick **Keep both** and **Send** again if you want it anyway.

## Checking the new file

Within about 15 seconds of qBittorrent finishing the download, the app starts checking it, by
itself, whether replacement is switched on or off. It checks every video file the download brought
— for a season pack, each episode's file on its own — before it touches anything:

1. **Complete.** qBittorrent, asked again, says the download finished without an error and that each
   new file is complete. A pack at 100 % doesn't say on its own which file is done.
2. **Readable.** The app finds the file in its own folders through qBittorrent's path mapping, in
   one of your library folders, and reads it: a regular file, not empty, with a video stream and a
   running time, of the size qBittorrent downloaded, and not one of your old copies. No other
   download in qBittorrent may write the same file.
3. **Seen by Jellyfin.** The app asks Jellyfin to look at the new files — again at its next check,
   within the hour, while Jellyfin doesn't take the request; it asks Jellyfin nothing else —, then
   reads every 15 seconds what Jellyfin made of each, until each is listed, read and identified. A
   trailer or another extra Jellyfin keeps beside the film holds nothing up.
4. **The same film or episode, by Jellyfin's ids.** A film's new file must carry your film's TMDb or
   IMDb id — your own TMDb link counts — and no other id of the same kind. An episode must be of the
   same series, by the series' ids, at the same season and episode number, and Jellyfin must still
   number your old episode, and place it in that series, as when you scheduled it. Each copy you
   ticked pairs with exactly one new file; a new episode no ticked copy pairs with — the extra
   episode a season pack brings, say — is simply added. The other films of a collection simply join
   your library too, once every copy you ticked found its new file.

**Jellyfin gets an hour.** Jellyfin looks at a new file about a minute after it is asked, then reads
and identifies it, which for a new series can take minutes. So the app waits up to an hour from the
moment Jellyfin took its request for each new file to be listed, read and identified, and up to an
hour from the start of the check for qBittorrent to answer. Meanwhile the **Jobs** page says the new
file is being checked and, once Jellyfin has the request, until what time the app waits for it. If
Jellyfin identified a new file wrongly, or not at all, you can identify it in Jellyfin yourself
within that hour, and the check then passes by itself; after the hour, fix it the same way and press
**Retry** (see [When a replacement stops](#when-a-replacement-stops)). A Jellyfin the app can't
reach never lets a file pass.

**When it stops.** If anything is missing or unclear, the replacement stops and says why, and both
copies stay. It stops as soon as it knows:

- qBittorrent reports an error for the download, no longer has it, or hasn't finished one of its
  files — "“qBittorrent” hasn't finished “…” (73 % done)."
- The app can't tell where a new file is — no path mapping covers it, or none of your library
  folders holds it —, or the new file is one of your old copies.
- Another download in qBittorrent writes the same file.
- Jellyfin identified a new file as another film while a copy you ticked has no new file — it may be
  that copy's, identified wrongly —, placed a new episode in another series, or gave a new file ids
  that disagree with yours — "“Living room” identified “…” as another work (IMDb tt0090605), not
  Alien (1979)." — or made a film of an episode, or the other way round.
- Jellyfin now numbers your old episode otherwise than when you scheduled the replacement, or places
  it in another series — "“Living room” now numbers the old copy “…” season 2, episode 3, not season
  2, episode 1 as when it was scheduled."
- A pair is unclear: two new files of one film or episode, none for a copy you ticked, a copy that
  is one half of an episode (its name glues an "a" or a "b" to its S03E09, say), or a file that
  holds two episodes where you ticked one, by Jellyfin's numbers or by its name.
- The new file's name claims another edition than the release did — "“…” claims Extended cut, while
  the release claimed Director's cut."
- The new file runs under three quarters of your old copy's running time, as the app measured it —
  "“…” runs 1:06:40, less than three quarters of the old copy's 1:33:24." A longer cut, an Extended
  or a Redux, is fine, and so is any length when the old copy's was never measured.

Once the hour is up, it stops with what is still missing, such as "“Living room” gave “…” no TMDb or
IMDb id within an hour, so it can't be told to be Alien (1979)." It stops that way, too, when
Jellyfin gave a new file only an id of a kind your film isn't known by in the app, and when
qBittorrent holds a download the app can't place in its folders — a magnet still fetching its list
of files, say —, as it can't tell whether that download writes the new file. A sample file in the
download stops it as well: Jellyfin ignores samples, so it never lists one. These show on the
**Jobs** page as "Replacement needs review: …". A new file that is no usable video — one the app
can't read as media, an empty one, one without a video stream or a running time — stops it as
"Replacement stopped: …".

**Verified.** When every check passes, the line gets a green tick: "New file verified: 1 old copy
moves into the quarantine next." Jellyfin shows both copies until the old one has moved; see [Moving
the old copy aside](#moving-the-old-copy-aside). A replacement this check stopped for review stays
as it is, both copies kept, until you settle it: fix the cause and press **Retry**, drop a copy, or
keep both; see [When a replacement stops](#when-a-replacement-stops).

## Moving the old copy aside

About 15 seconds after the new file is verified — the app looks every 15 seconds, and right after it
starts —, the app takes the replacement up, as long as replacement is switched on. While it is off,
the replacement waits, verified, and its line says that nothing will move while it is off. Before
anything moves, it checks the old copies once more:

1. **Still the copy you picked.** For each copy you ticked: still inside the **Media folders** and in
   a folder ticked for replacement, no clip of a Blu-ray or DVD folder, still at its path with the
   same device, inode, size and modification time as when you scheduled it, a file itself rather
   than a link to one, not the new file itself, and its new file still the one verified. Otherwise
   the replacement stops for review, such as "“/media/movies/Alien (1979)/Alien.mkv” changed since it
   was picked for replacement, so it stays where it is." A copy whose folder you untick stops the
   whole replacement this way, not just that copy, and the Jobs line says so beforehand.
2. **No torrent holds it.** The app reads every download client's torrents with their files once more
   — every client whose paths can reach the **Media folders**, and every client it has sent a
   replacement to, whatever its path mappings say — for every file that would move.
   A video any torrent lists, in any state, stops it: "Still held by the torrent
   “Alien.1979.Remastered.1080p” in “qBittorrent”: remove that torrent there without its files, then
   press Retry." — or, held by several, "Still held by the torrents “…” in “qBittorrent” and “…” in
   “seedbox”: remove those torrents there without their files, then press Retry." A client it
   couldn't read, or torrents it couldn't place in its folders, stop it too, as it can't tell: "The
   app couldn't tell whether a torrent in “qBittorrent” holds the old copy: …". If a client's path
   mappings under **Integrations** were deleted, or pointed outside the **Media folders**, after a
   replacement went through it, its torrents land outside the **Media folders**, where the app never
   looks, and one that lists a file with the name or the size of a file that would move, or with no
   known size, stops it too: "“qBittorrent”'s path mappings put 1 of its torrents outside the Media
   folders, so the app can't tell whether that torrent holds the old copy: check those mappings under
   Integrations, then press Retry." Put the mappings back, then press **Retry**; a copy no torrent
   lists anything like still moves, and so does a copy with another name (a hardlink) when a torrent
   there lists only a file of its size under another name: that is the torrent's own name of it, as
   `/data/torrents` hardlinked into `/data/media` seeds it, and it keeps seeding. A subtitle or
   `.nfo` a torrent lists stays where it is, named on the job, and the video still moves. A copy that
   is only another name (a hardlink) of a torrent's file may move, since the torrent keeps its own
   name; it frees no room while the torrent keeps its file. The app never removes, stops or changes a
   torrent: remove it in qBittorrent without its files, then press **Retry**.

**What moves.** The video you ticked, and each file beside it named after it — `Alien.srt`,
`Alien.uk.srt` and `Alien.nfo` beside `Alien.mkv` —, never the folder, which stays, never another
video, never another video's own files (beside `Alien (1979).mkv` and `Alien (1979).2160p.mkv`,
`Alien (1979).2160p.uk.srt` belongs to the second and stays), and never a disc folder's clips,
which stop the replacement for review.

**Where.** Into `.mam-quarantine` at the top of the **Media folders** folder that holds the copy, in
a folder of the replacement's own, keeping where each file was: `Alien.mkv` from
`/media/movies/Alien (1979)/` goes to `/media/.mam-quarantine/<replacement>/movies/Alien (1979)/`.
Each file moves by one rename, which on Linux never replaces a file and never copies one, so the
quarantine must be on the same mount as the copy; before each file the app reads the switch and the
ticks again, and after it the moved file must still be the same file.

**When a file can't move.** A video that can't move stops the replacement for review with why, such
as "“Alien.mkv” couldn't be moved into the quarantine: …", and what already moved — earlier
episodes of a season, say — stays in the quarantine, listed on the job. A subtitle or `.nfo` that
can't move stays where it is, named on the job, and its video still moves. Switching replacement
off, or unticking the folder, while the files move stops it the same way: "Replacement was switched
off while the old copies were moving: 1 of 3 names is in the quarantine." In the rare case that
another file took a file's place in the very moment before its move, that other file is what moved:
the job says so, marks the old copy's file as not found, and stops for review. Nothing is ever
deleted because a move couldn't be made.

**What you see then.** The line says "Old copy moved into the quarantine: 1 copy, kept until you
restore it or delete it for good.", and "1 file stayed in its folder: see the job." when a file
stayed. The app tells Jellyfin that the old copy's files went — the same one request it sends for a
new file, asked again within the hour while Jellyfin doesn't take it, never naming the quarantine,
which Jellyfin never sees —, and Jellyfin drops the old copy's card about a minute later. Your
watched state passes to the new card only when Jellyfin does it by itself: when both copies sat side
by side in one folder and the new card already has the same TMDb or IMDb id. Otherwise — an old film
in a collection's folder, an episode in another show's folder — Jellyfin keeps it aside, and it
comes back if you restore the old copy. The old copy also leaves the collections and playlists you
added it to by hand, and the new one isn't added to them. The Library page's **Scan folders** never
looks into a quarantine.

**A restart.** If the app stops while files move, the first pass after it starts looks each file
up, by its device and inode, where it was and in the quarantine, records where it is, and stops the
replacement for review: "The app stopped while moving the old copies: 2 of 3 names are in the
quarantine." It moves and deletes nothing by itself then. The same goes for a Restore or a Delete
for good the restart cut — unless every file was already back, or deleted, which ends it as the
Restore or the Delete for good would have. A file it can't read then, or whose folder isn't there
— a disk not mounted yet —, leaves the replacement as it is until a later pass can tell.

**Retry.** For a replacement this move stopped — before it, as a torrent holds the copy or a copy
changed, or during it, as a file couldn't move, the switch was turned off or the app restarted — the
owner gets **Retry**, on the Jobs page beside the line and on the job's page. It writes nothing to
the disk: the replacement is verified again, and the next pass checks everything again before the
rest moves — the subtitles and `.nfo` left behind beside a video that already moved included —; what
is already in the quarantine stays there. Instead, you can drop the copy in the way — it stays where
it is, and the others move once you press **Retry** — or, while nothing has moved yet, keep both;
see [When a replacement stops](#when-a-replacement-stops).

## Restoring or deleting a quarantined copy

A job that carries a replacement has a **Replacement** section on its page, between its details and
its files, for the owner alone. Once the move has begun, its **Files the move planned** lists every
file the move planned — the video, then its subtitles and `.nfo` — with where it was, its place in
the quarantine under it, its size and where it is now, the reason when one stayed, and how much room
the replacement takes in the quarantine. Everyone else reads "Only the installation owner sees a
replacement's copies and checks, and retries, cancels or drops them." Nothing in the quarantine goes
by itself: no timer, no cleanup.

**Restore** is offered whenever something of the replacement is in the quarantine, also after it
stopped for review. It asks once, "Put the old copy back?", then puts every file back where it was by
the same kind of rename — never over a file that is there now, and never into a folder that is gone,
as it creates no folder. Before anything moves it checks every file, and refuses with nothing moved
when one can't go back: "“/media/movies/Alien (1979)/Alien.mkv” already holds a file, so nothing was
put back.", "The folder “/media/movies/Alien (1979)” is gone, so nothing was put back; the app
creates no folder.", a file that changed in the quarantine, or a folder no longer ticked. After a
**Delete for good** that stopped part-way once a video was deleted, Restore isn't offered, as the
subtitles alone would go back: press **Retry**, then **Delete for good** what is left. Then the
line says "Replacement undone: the old copy is back where it was.", and your new copy stays as it
is, so you have both again. The app tells Jellyfin the files came back; Jellyfin finds the same item
again, with its watched state, and identifies it afresh, so a TMDb link you set by hand may need
**Identify** again (the Library says when Jellyfin lost it). A torrent you removed for the move
doesn't come back: to seed it again, add it in qBittorrent yourself. A file that can't go back
part-way stops it for review, saying how many files are back.

**Delete for good** is offered once the replacement rests in the quarantine. It asks once more,
listing every file it will delete with its size and how much room that frees — "Frees 4.2 GiB." —
and how many files have another name (a hardlink) on the disk now, which frees nothing. Right
before deleting it reads each file again, and deletes nothing when one changed, or when what the replacement holds
changed since you opened it ("What this replacement holds in the quarantine changed since you opened
it. Open Delete for good again."). It deletes those files from the quarantine and nothing else, not
even the replacement's folders there, which stay empty. Then the line says "Replaced: the old copy
was deleted for good." This can't be undone. The room comes back once nothing holds the file open —
a player still streaming it, say.

While replacement is switched off, both are disabled with "Replacement is switched off on the Media
folders page: nothing is put back or deleted while it is off." Only the owner restores or deletes,
and every file's step writes a row in the app's audit trail.

The **Media folders** page keeps the quarantine within reach: it lists how much room each quarantine
takes ("/media/.mam-quarantine: 4.2 GiB in 2 files, from 1 replacement.", or "The quarantine is
empty."), and refuses a **Save** that would take out the folder whose quarantine still holds old
copies — "“/media/.mam-quarantine” still holds replaced copies, so its media folder can't be taken
out of the list. Restore them or delete them for good first." A folder that holds it, put in its
place, keeps it within reach; the quarantine itself doesn't.

## On the Jobs page

A job that carries a replacement says where it stands, in a line under its status:

- "Replacement scheduled: 1 copy, kept until the new one is verified." — while the download is sent
  and downloads.
- "Replacement checks the new file: 1 copy, kept until it is verified." — once the download is done,
  while its new file is checked.
- "Replacement waits for Jellyfin to identify the new file until 14:05: 1 copy, kept until it is
  verified." — once Jellyfin has the request to look at the new file, until its hour is up.
- "New file verified: 1 old copy moves into the quarantine next." — with a green tick, once every
  check passed.
- "Moving the old copy into the quarantine…" — while it moves.
- "Old copy moved into the quarantine: 1 copy, kept until you restore it or delete it for good." —
  once it rests there, followed by "1 file stayed in its folder: see the job." when one stayed.
- "Putting the old copy back…" and "Deleting the old copy for good…" — while the owner's **Restore**
  or **Delete for good** runs.
- "Replacement undone: the old copy is back where it was." — after **Restore**.
- "Replaced: the old copy was deleted for good." — with a green tick, after **Delete for good**.
- "Replacement needs review: …" with why — the check or the move stopped, or the download couldn't
  be told apart from qBittorrent's other downloads — and what to do: "Fix it in Jellyfin or
  qBittorrent, then press Retry — or see the job." after the check, "1 copy can only be dropped, or
  both kept: see the job." while a copy only a drop settles is in it ("A new check can't pair its
  last copy: keep both." once it is the last one left), and "Keep both, or cancel the job." for a
  download the app can't follow; after the move, its reason says what to do. The owner's **Retry**,
  where it can help, and **Keep both** sit beside it. On the job's own page the line leaves what to
  do to its **Replacement** section.
- "Replacement stopped: …" with why — the download failed or was cancelled, or a new file is no
  usable video. A failed job says only "Replacement stopped.", as its own error already says why.

While the download goes on, while its new file is checked and once it is verified, the line also
says when replacement has been switched off — nothing will move while it is off — and when a copy's
folder is no longer ticked: "1 copy is no longer in a ticked folder: unless it is ticked again, the
replacement stops for review and nothing moves." A replacement that stopped — one that needs review,
failed or was cancelled — goes no further until the owner acts, so its line says none of that; one
that needs review still keeps its copies. Once you dropped a copy, the line adds "1 copy dropped."
and counts only the copies still in the replacement. The page asks again every 2 seconds while a
download goes on, its new file is checked, a verified copy waits to move with replacement on, or
files move, come back or are deleted, so you see how it ends without reloading. **Cancel job** also
ends the replacement while the download goes on: both copies stay, and the torrent stays in
qBittorrent, as before. A download that is done can't be cancelled there, as before.

The owner's row also has **Keep both**, before **Cancel job**, which cancels only the replacement —
once the download is done too — and lets the download go on, and **Copies**, which opens right under
the job the old copies you ticked, each with its new file, where it stands and **Drop**, asking
again every 2 seconds while the check runs. See [When a replacement
stops](#when-a-replacement-stops).

## When a replacement stops

A replacement that stops for review keeps both copies and waits for you: nothing of it goes on by
itself. The **Jobs** page's line says why and what to do, and the job's page shows the whole of it
in its **Replacement** section, for you alone:

- **What you can do**, by what stopped it — such as "Fix what the reason says — for a film Jellyfin
  gave no id, set its TMDb link on the Library page, and Jellyfin's Identify applies it —, then
  press Retry: the check starts again, and Jellyfin's ids decide. Or drop a copy below: it stays
  where it is. Or keep both.", without the drop when no copy can be dropped, as for a single film —,
  with **Open Alien in Library** for a film Jellyfin gave no id, and a word when replacement is
  switched off.
- **How far the check got** — "Reading the new files on the disk (started 13:05).", "Waiting for
  Jellyfin to identify the new files until 14:05.", "Every old copy is paired with a new file
  Jellyfin identified." or "The check stopped." —, so you know how long a fix in Jellyfin can still
  let the check pass by itself.
- **Your old copies** — each copy you ticked, with its size, running time, episode and edition, the
  new file it pairs with, and where it stands: "Kept until the new file is verified.", "Paired with
  its new file: it moves into the quarantine when the replacement goes ahead.", or "Stopped the
  replacement:" with why, such as "Still held by the torrent “Alien.1979.Theatrical” in
  “qBittorrent”: remove that torrent there without its files, then press Retry." Above them:
  "Nothing moves until every copy is paired or dropped: 1 of 2 paired, 1 dropped."
- **The new files** — each video file the download brought, with how far it got on the disk and in
  Jellyfin — "Not listed by Jellyfin yet.", "No TMDb or IMDb id from Jellyfin yet.", "Identified by
  Jellyfin." or "An extra: simply added." —, beside the ids your film or series is known by in the
  app.
- **Files the move planned** — what moved into the quarantine or stayed, once the move has begun;
  see [Restoring or deleting a quarantined copy](#restoring-or-deleting-a-quarantined-copy).

On the **Jobs** page, **Copies** on the job's row opens the same old copies right under it. Both
pages ask again every 2 seconds while the check runs.

**Fix it, then press Retry.** When the check of the new file stopped — Jellyfin gave it no id, or
another film's, say —, correct the new item in Jellyfin: for a film, set its TMDb link on the
**Library** page, which **Open Alien in Library** opens searched by its title, and Jellyfin's
**Identify** applies it. Then press **Retry**: the app checks the new files again from the start —
qBittorrent's word, the files on the disk, a new request to Jellyfin to look, and an hour for each
again —, and Jellyfin's ids decide once more whether the old copy moves; Jellyfin's new look keeps
the ids you set. When a torrent holds the old copy, remove that torrent in qBittorrent without its
files, then press **Retry**: the old copy is checked once more, and moves. A **Retry** with nothing
fixed stops again with the same reason, and moves nothing. A replacement whose download couldn't be
told apart from qBittorrent's other downloads has no **Retry**: keep both, or cancel the job.

**Drop a copy.** **Drop**, on a copy of a replacement that stopped, takes that copy out of the
replacement once you confirm: it stays where it is, never moves with this replacement, and a new
file it was paired with is simply added to your library once Jellyfin has identified it. Nothing
else happens until you press **Retry**, so drop each copy you need to, then press **Retry** once:
the other copies are checked again, and move. The last copy can't be dropped — "It is the
replacement's last copy: keep both instead." A dropped copy stays on the job's page, greyed, with
its last problem; it can't be taken back in, and another download may replace it later.

**Some stops only a drop settles.** When Jellyfin now numbers your old episode otherwise than when
you scheduled it, when no new episode is at its number, when the old copy or the new file is half an
episode or holds several, when the new file's name claims another edition than the release did, or
when it runs under three quarters of your old copy, nothing you fix in Jellyfin can pair them. The
copy says "Only dropping it or keeping both settles this.", and **Retry** waits until it is dropped:
the job's page shows it disabled with "Drop the copies a new check can't pair first, or keep both.",
and the **Jobs** page leaves it out. When it is the last copy left, which can't be dropped, only
keeping both settles it: "A new check can't pair the copies left, and the last copy can't be
dropped: keep both instead." No click confirms a film, an edition or a pair by hand: Jellyfin's ids
decide, or you drop the copy, and nothing moves until every copy you ticked is paired or dropped.

**Keep both.** **Keep both** cancels only the replacement, at any point before an old copy starts to
move — while the release downloads, while its new file is checked, once it is verified, or in
review: both copies stay, the download goes on, and nothing is sent to qBittorrent. It asks first —
"Keep both copies of …?", with **Keep both** and **Keep replacing** — and can't be undone; the line
then says "Replacement stopped: You cancelled the replacement, so nothing will be replaced.", and
another download may replace those copies later. Once part of the replacement is in the quarantine,
it is refused: **Restore** puts that back. **Cancel job** still stops following the download, and
ends the replacement with it, while the download goes on.

**Only the owner, and every step recorded.** Only the owner sees a replacement's copies and its
check, and retries, keeps both or drops; everyone else reads "Only the installation owner sees a
replacement's copies and checks, and retries, cancels or drops them." Each step writes a row in the
app's audit trail, none writes anything to your media folders or to qBittorrent, and all of them
work while replacement is switched off, as they move nothing.

## Turning it on

Replacement is off after the upgrade, and no folder is ticked. Only the owner can turn it on, in
four steps:

1. **Mount the media folders read-write.** In `docker-compose.yml`, drop `:ro` from the media mount
   if it has it (`- /mnt/media:/media` rather than `- /mnt/media:/media:ro`); a mount without it is
   read-write already. Each folder you allow under **Media folders** must be one mount holding its
   libraries, with nothing else mounted inside it, so that its quarantine sits on the same mount as
   your copies: a move across two mounts would be a copy, and the app refuses it. The change takes
   effect when the app starts again in step 2.
2. **Run the app as the media folders' owner.** First make sure the `app` service in your
   `docker-compose.yml` has the `user:` line that 0.3.0's has, and add it under `restart:`, at the
   same indent, if it hasn't:

   ```yaml
       restart: unless-stopped
       user: "${APP_USER_ID:-10001}:${APP_GROUP_ID:-10001}"
   ```

   A `docker-compose.yml` taken when 0.2.1 or an earlier version came out hasn't got it, and
   updating with `bash deploy.sh` doesn't add it, as it changes no file. Without it the ids below do
   nothing: the app keeps running as the image's own user, 10001, and once the data volume is handed
   over to other ids it can't open its own data and restarts over and over. Instead of adding the
   line you can take 0.3.0's `docker-compose.yml` and put your media mount, and anything else you
   changed, back into it.

   Then, in `.env`, set `APP_USER_ID` and `APP_GROUP_ID` to the user and group that own your media
   files — usually qBittorrent's PUID and PGID, 1000 and 100 on the reference setup;
   `docker compose config | grep 'user:'` then shows them, and shows nothing while the line is
   missing. The app's data volume belongs to the app's old ids, so hand it over once, from the
   folder of `docker-compose.yml`, with the app stopped and its data backed up first — `mam.db` and
   `.secrets/` together, as the key in `.secrets/` is what reads the integration credentials
   `mam.db` keeps:

   ```bash
   docker compose stop app
   docker run --rm --volumes-from media-acquisition-manager -v "$PWD:/backup" alpine tar czf /backup/mam-data-before-handover.tgz -C /data .
   docker compose down
   docker compose run --rm --no-deps --user 0:0 --entrypoint chown app -R 1000:100 /data
   ```

   with your own ids in place of `1000:100`. The archive holds the app's secrets, so keep it where
   only you can read it. No file or folder of yours changes owner or permissions; with these ids the
   app may write wherever that user may, and only the switch and the ticks below keep a replacement
   to the folders you tick. Then start the app again with `bash deploy.sh`, which waits until it
   reports healthy and otherwise prints its log (`docker compose up -d` starts it too, without
   waiting). If it doesn't start and its log says `Permission denied`, or that it can't open its
   database, it runs under other ids than the volume was handed to — the `user:` line or the ids in
   `.env` are missing —: fix that and start it again; nothing is lost.
3. **Switch it on.** Open your user menu → **Media folders**. Under **Folders the app may read**,
   make sure the folder that holds your libraries is there, as the app sees it (`/media`, say); one
   you add there now has to be saved with **Save** before the library folders under it can be
   ticked. In the **Replacing copies** card below, tick **Replace copies after verification**.
4. **Tick the library folders.** Under **Library folders replacement may touch**, tick each library
   folder whose copies may be replaced — `/media/movies` for «Фільми», say. A folder outside the
   **Media folders** can't be ticked. A library folder inside another one needs its own tick: a
   copy counts only when every library folder that holds it is ticked. As soon as you tick a
   folder, it says whether a move into the quarantine can work there: "A move into the quarantine
   can work here: the same mount as the quarantine, mounted read-write, and writable by the app.",
   or a line for each thing in the way, which also says what to do — "Not on the same mount as its
   media folder's quarantine, so a move would fail: mount the media folder as one read-write
   mount.", "Mounted read-only, so a move would fail: mount the media folders read-write." or "The
   app's user can't write here or in its media folder, so a move would fail: run the app as the
   media folders' owner." —, and, when it couldn't look, "The app couldn't check whether a move can
   work here; the move itself will tell." That line looks at the ticked folder itself and at the top
   of its media folder, where the quarantine goes, never at the folders inside it: it can say a move
   can work while a copy sits in a folder of its own that the app's user can't write to — one that
   root owns, say —, and that copy's move then stops for review with "“Alien.mkv” couldn't be moved
   into the quarantine: The app's user isn't allowed to change
   “/media/movies/Alien (1979)/Alien.mkv”: renaming or deleting a file needs write and search
   permission on its folder, and on the one it goes into.", the copy staying where it is. Choose
   **Save**: the folders, the switch and the ticks are saved together.

**Replace after verification** in the **Download** dialog can then be picked, by you alone; until
then it is there but can't be picked, and once a destination is picked it says "Replacement is
switched off. Switch it on, and tick the folders it may touch, on the Media folders page." A job
that carries a replacement offers you **Retry**, **Keep both**, **Drop**, **Restore** and **Delete
for good** where each applies. For a copy to be ticked in the dialog, the app must also have
inspected it (the **Library** page's **Inspect files**, or the inspection after each sync), and the
destination's category must save inside one of your library folders under the **Media folders** —
the **Destinations** page says whether it does. The marks of torrents that hold a copy need qBittorrent 5.2 or later, and so do the
check of the new file and the check right before the move: with an older qBittorrent the app can't
tell whether another download writes the new file, or whether a torrent holds the old copy, so every
replacement stops for review there.

Quarantined files stay on disk in `.mam-quarantine` at the top of the media folder, outside the
database backup: backing up `mam.db` and `.secrets/` doesn't keep them, and restoring a backup
doesn't bring them back. A replacement needs room for both copies until you delete the old one for
good.

Switching replacement off again leaves **Keep both** only in the dialog. Replacements scheduled
before keep following their downloads, and their new files are still checked, as that moves nothing;
but nothing moves into the quarantine, comes back out of it or is deleted from it while replacement
is off, and the **Jobs** page and the job's page say so. **Keep both**, **Drop** and **Retry** still
work on them then, as they move nothing.

**Going back.** Switching replacement off is enough to stop it. To run the app under the image's
own ids again, or to go back to 0.2.1, first settle the quarantine, while replacement is still on
and the app still runs as the media folders' owner, as nothing is put back or deleted while it is
off: **Restore**, or **Delete for good**, every replacement with a copy in the quarantine, and
**Keep both** on every other one still under way or in review, so none is left half-way. Neither
way back can do it afterwards: under its old ids the app may not change the quarantine's folders,
which it made as the media folders' owner, and 0.2.1 knows nothing of the quarantine — its **Scan
folders** would list what is left there as files no library reported. Then switch replacement off,
choose **Save**, and hand the data volume back, from the folder of `docker-compose.yml`:

```bash
docker compose down
docker compose run --rm --no-deps --user 0:0 --entrypoint chown app -R 10001:10001 /data
```

Take `APP_USER_ID` and `APP_GROUP_ID` out of `.env` — the `user:` line can stay, as without them it
gives the image's own 10001 —, set `APP_TAG=0.2.1` there if you go back to 0.2.1, put `:ro` back on
the media mount if you like, and start the app again with `bash deploy.sh`. 0.3.0 only added tables,
columns and indexes to the database, and 0.2.1 leaves them alone.

## Your files

Scheduling a replacement and checking its new file only read. Once a destination is picked, the app
looks at your copies on the disk — each one's device, inode, size and modification time, the
identity it keeps with the replacement so the move can find the very same file again —, and when you
pick **Replace after verification** it also reads each download client's list of torrents with their
files, and reads it again right before the move. Once the download is done, it reads the new files —
their identity, and what the media inspector finds in them — and asks qBittorrent about the download
and its other downloads.

What it writes to the media folders is the quarantine and nothing else: the folder `.mam-quarantine`
at the top of a media folder and a folder for each replacement inside it, the renames of the old
copies' files into it and back out of it, and the deletions from it of the files you delete for
good. It creates, renames or removes no other folder, never writes over, copies, changes or deletes
a file anywhere else, and changes no file's owner or permissions. It writes nothing to qBittorrent
but the one add of the release you sent, as every download does, and never stops, removes or changes
a torrent. **Keep both**, **Drop** and **Retry** write only to the app's own database, nothing to
your media folders or to qBittorrent; the check a **Retry** starts asks Jellyfin to look at the new
files again. It asks Jellyfin to look at the new files' paths, and at the old copy's paths after it
moves and after it comes back — the request Jellyfin's own folder watcher makes when a file appears
or goes — and otherwise only reads Jellyfin: it never changes, refreshes, identifies or deletes an
item there. What it keeps — the copies you ticked, the works they are copies of, your confirmation,
who scheduled it and when, what each check found, the copies you dropped, and where each old file
went and when, with a row in the app's audit trail for each step and each file — stays in the app's
own database; the files in the quarantine stay on the disk, outside the database backup.
